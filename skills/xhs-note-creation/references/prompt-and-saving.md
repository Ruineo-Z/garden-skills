# 提示词与保存

## 生成提示词的组织方式

封面和后续配图使用结构化 JSON 组织最终提示词。JSON 是交给图片模型的提示词文本，不是 API 请求体；本地 Agent 将它和实际参考图传给 [生图脚本](image-tool.md)。

摄影推导用于做选择，最终提示词用于描述所选照片。把光影、构图和人物引导的结论放入现有字段，无需另加一套摄影流程或推导记录：

```json
{
  "type": "小红书穿搭配图",
  "goal": "本张图片的用途、想传达的感受与展示重点",
  "references": [
    {
      "id": "REFERENCE_0",
      "source": "商品图路径或可追溯标识",
      "role": "商品外观、颜色、材质、结构和可行穿戴方式"
    }
  ],
  "subject": {
    "person": "人物身份与可辨认的外貌特征；后续配图以已确认封面为身份依据，不固定封面上的表情和朝向",
    "hair_and_makeup": "画面可见的发型和妆容",
    "outfit": "服装款式、颜色、层次及搭配依据",
    "product_wearing": "商品相对身体的位置、接触、受力和垂落",
    "pose": "当前瞬间由人物状态推导的表情、视线、身体和脸部朝向、手的位置、支撑和重心"
  },
  "scene": {
    "background": "背景环境和需要保留的空间关系",
    "position": "人物在实际环境中的位置，以及人物、商品与周围物体的接触或空间关系",
    "lighting": "现场光源方向与软硬，脸部、商品及背景的明暗关系"
  },
  "composition": {
    "camera": "谁持机、摄影者所在位置、机位方向和拍摄关系",
    "framing": "人物在画面中的位置与大小、上下左右留白及其与背景结构的关系，再说明景别、取景范围和必要裁切",
    "visual_focus": "第一视觉重点",
    "aspect_ratio": "3:4"
  },
  "style": {
    "finish": "穿搭博主用手机拍出的照片",
    "color_and_retouching": "色调、符合景别的皮肤与材质表现、现场感和适度修饰"
  },
  "constraints": {
    "must_keep": [],
    "avoid": []
  }
}
```

## 参考图映射

参考图按实际输入顺序编号，并在 JSON 的 `references` 中逐一说明：

- 封面：`REFERENCE_0` 通常是商品图，`REFERENCE_1` 是对标图；模特图按实际输入顺序追加。
- 后续配图：商品图负责商品，已确认封面负责人物身份；新背景或姿势参考按实际输入顺序追加。
- 修改：`REFERENCE_0` 是目标原图；商品图、封面或新背景只有在确实用于修改时才追加。

对标图的职责只能是它实际提供的环境、光影、构图或姿势参考，写明需要借鉴的画面关系，不把原图人物、服装、文字、贴纸或平台元素默认为必须保留。后续配图的封面参考职责写清“保持同一人物身份和可辨认的外貌特征，当前表情、视线、头部朝向和构图按本张描述重新设计”。不把它写成整张图片或脸部状态的复制要求；服装与环境是否延续按后续配图规则和当前请求判断。

## 提示词表达要求

- 先写已确定的照片类型和用途，再写主体、场景、构图、质感和约束。
- 每个决定只表达一次，不在多个字段中写互相冲突的要求。
- `person` 描述身份特征，`pose` 描述当前表情与动作，`scene.position` 描述人在实际环境中的位置，`composition.framing` 描述人在画面中的位置、大小和留白。身份约束不使用“脸部完全一致”或“表情不变”代替具体职责；`must_keep` 只放实际需要延续的内容，不默认加入封面的表情、机位或构图。
- 描述成片中的状态，不把摄影师的指令、方案选择过程或不可见的故事当作画面描述。动作原因可以帮助内部推导，最终落实为身体、表情、视线和布料的可见变化；一张照片不承载连续多个动作阶段。
- 只写镜头可见或会影响成片的关系；不写画面外无关细节。
- 不用“自然姿势”“高级感”“氛围感”替代手的位置、披肩状态、人物与环境关系等具体内容。
- 抽象感受可以放在 `goal` 中说明意图，但必须由光影、构图和人物状态共同体现。例如“温柔”需有相应明暗和表情，“旅行感”需有相应空间和环境关系，不固定使用某种光线或姿势。
- 商品外观以商品参考图为准；提示词只补充穿戴方式和必要结构限制。
- 默认封面没有文字；用户要求时再加入 `text_overlay` 或等价的排版字段，并说明文字位置、内容和不遮挡主体的要求。
- 默认比例为 3:4，用户明确指定其他比例时遵从用户要求。

## 保存目录

在当前 Agent 的默认工作目录下，为每篇笔记建立一个独立目录：

```text
<Agent 默认工作目录>/
└── YYYY-MM-DD-笔记名称/
    ├── cover.png
    ├── cover.md
    ├── 1.png
    ├── 1.md
    ├── 2.png
    ├── 2.md
    └── note.md
```

- 目录名由当天日期和笔记名称组成；一个目录只保存一篇笔记。
- `cover` 是封面，`1`、`2`、`3` 表示后续配图顺序。
- 图片和提示词使用相同的主文件名；图片扩展名按实际格式保存，不把 JPEG 或 WebP 仅改名为 PNG。
- 修改版本使用 `cover-v2`、`1-v2`、`1-v3` 等名称，保留原文件。
- 笔记名称只做必要的文件名清理，避免路径分隔符和覆盖，不改变用户可识别的名称含义。
- 标题与正文按 [文案交付与保存](copy-and-saving.md) 保存到同目录的 `note.md`，与图片提示词记录分开。

## Markdown 记录

每张图片对应一个 Markdown 文件，至少保存：

````markdown
# <封面或配图编号>

## 最终提示词

```text
<实际交给图片工具的完整提示词>
```

## 参考图

- REFERENCE_0：<路径或标识>；用途：<职责>
- REFERENCE_1：<路径或标识>；用途：<职责>

## 状态

- 类型：<封面 / 后续配图 / 图片修改>
- 交付：<仅提示词 / 等待确认 / 已生成 / 生成失败>
- 图片：<实际路径；未生成时不填写>
- 说明：<失败、归档或版本信息>
````

提示词只交付或等待确认时，仍保存完整待执行提示词；这两种状态不是生成失败。保存失败时如实说明，不能填写不存在的文件路径。

脚本接收单独的原始提示词文件，不接收上面的 Markdown 记录。调用前将最终 JSON 或修改指令原样保存为笔记目录中的 `<主文件名>.prompt.json` 或 `<主文件名>.prompt.txt`；脚本将实际发送的内容写入同名 `.md`。如果已有仅提示词或等待确认的 `.md`，先将其保留为 `<主文件名>-待确认.md`，再调用脚本，不覆盖旧记录。
